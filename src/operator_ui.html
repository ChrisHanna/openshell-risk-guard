How it works

OpenShell decides what an agent may reach. Risk Guard decides whether this call, from this workload, right now, looks like its normal behavior. It can only say no.

Risk Guard adds one layer on top of OpenShell. It never widens what OpenShell allows.

The path of one request

Click a step, or a part of the diagram, to see what happens there.

Two places Risk Guard plugs in

Both are OpenShell extension points. Nothing in OpenShell is forked or patched.

On every request supervisor middleware

Scores each outbound HTTP call after OpenShell's own rules allow it and before any secret is attached.

Registered as a supervisor middleware, bound per sandbox in its policy (network_middlewares) for the hosts you attach, with on_error: fail_closed. HTTP request, phase PRE_CREDENTIALS; 500 ms timeout.

On every sandbox change gateway interceptor

Checks that nobody removes Risk Guard or widens a sandbox's access, and records each sandbox so its activity has an identity.

VALIDATE (fail-closed) covers CreateSandbox, UpdateConfig, ApproveDraftChunk, ApproveAllDraftChunks and SubmitPolicyAnalysis. POST_COMMIT records the epoch and policy snapshot, and DeleteSandbox closes the epoch. OpenShell forces POST_COMMIT to fail-open because it observes an already-committed change, so a missed event cannot deny anything.

Who is the "workload"?

Scores follow a workload, not a sandbox, so a fresh sandbox does not reset the penalty.

A workload is a workspace plus the identity OpenShell authenticated for whoever created the sandbox. Nobody types it, so it cannot be forged. An agent can also carry a named identity, such as its Microsoft Entra application ID, but only when an allowlisted operator sets it.

Derived as a hash of (workspace, provider, kind, subject) from the gateway's authenticated principal, or taken from the openshell.nvidia.com/agent-id label when the creating principal is on the binding allowlist. A bad label is refused at VALIDATE.

What it stores, and what it never uses

Stores: the method, host, path pattern, a keyed resource name, the score and why, lock state, and the sandbox's policy. Never uses: request or response bodies, headers, query strings, or credentials.

OpenShell delivers the body, headers and query to the middleware, up to the registered payload limit. Risk Guard discards them unread, never logs them, and advertises the 4 MiB platform maximum so a large body is never denied just for its size. Raw resource names are stored, so keep the database on an encrypted volume.

What this is, and where NVIDIA Sentry fits

NVIDIA's own material, summarized. These are vendor claims this project has not verified.

For threat-level protection

The recommended approach is OpenShell plus NVIDIA Sentry: an out-of-band layer on BlueField-4 hardware that inspects requests, checks behavior against a profile, and can quarantine an agent without the host's cooperation. DOCA Argus adds host-level evidence from a BlueField DPU.

NVIDIA lists Sentry as planned, with some DOCA components available now for experimentation.

What this project is

Risk Guard was built to learn how to integrate with OpenShell. It adds visibility (why each request was allowed or blocked, per workload) and data for improving policies (learned behavior and tighter policy candidates). On Azure there is no access to BlueField, so it also acts as a software stand-in.

It is a prototype, not a threat-protection product. Its checks run next to the workload, so it assumes an uncompromised supervisor and node. The hardware layer keeps working if the host is compromised; Risk Guard does not.

Adopting it

What it takes, and what to expect.

What you set up

  • Run Risk Guard (one Deployment, one SQLite file on a volume).
  • Register its two services in the OpenShell gateway configuration and restart the gateway.
  • Add network_middlewares: risk-guard to a sandbox policy for each host you want scored, and give each agent an approved task profile.
  • Start in observe mode if you want detection before enforcement.

Honest limits

  • Fail-closed. If Risk Guard is down or slow, calls to attached hosts are denied. The gateway will not start if a registered service is unavailable.
  • One replica, one writer. No high availability yet. A redeploy leaves a gap of about a minute.
  • Only attached hosts, only HTTP. No scoring of other hosts, files, processes, responses or WebSocket traffic.
  • Early scores are rule-based. Until a workload has history, a score comes from its approved task rules and a fixed API-risk map, not learned behavior.
  • Recorded, not proven. A decision shows what was asked and answered, not that the call reached its destination.

Words used in this console

Workload
The identity a score follows across runs and sandboxes. Shown with its name and, for a named agent, its Application ID.
Sandbox
The isolated environment OpenShell runs an agent in. Sandboxes come and go; workloads persist.
Epoch
One governed lifetime of a sandbox: its policy, its approved baseline, and its decision sequence.
Task profile
The approved description of what a kind of agent is meant to do: allowed actions, approved resources and normal pace.
Score
0 to 100 for one request. It is not a probability of compromise. A request at or above the block line (70 by default) is denied.
Lock
A restriction on one kind of action against one target for a workload. It follows the workload across sandboxes, has no expiry, and only an operator can clear it.
Fail-closed
When Risk Guard cannot answer in time, the request is denied. That is an availability choice, and it is not recorded as risky behavior.
Enforcement
The tab showing what a workload is allowed to do and the saved settings. (Not NeMo Guardrails, which screens a task before an agent starts.)

Where each claim comes from: OpenShell's supervisor-middleware and gateway-interceptor documentation and source, and Risk Guard's design notes. This page describes the system as built; it is not a promise of future features.
